perf(group): 群在线集 —— 扇出预筛从 O(群成员数) 降到 O(群在线人数)

改造第 6.5 项「群维度 pub/sub」的第一步：先消灭扇出里两处对全部群成员做功的开销。

背景（§3.14 实测，万人群 1000 在线）：单条消息扇出 125ms 里，
presence MGET 占 44.7ms、成员列表展开+过滤占 27.7ms，合计 58%。
两者都是对「全部 10000 名成员」做功，与在线人数无关，是硬天花板。

改动：
- 新增 im:group:online:{groupId} 在线成员集（SET，元素为十进制 userId 字符串）
- 新增 GroupOnlineService：上线 SADD、下线 SREM、扇出时 SMEMBERS
- UserEventListener 接上 ONLINE/OFFLINE 钩子维护该集合
- GroupMessageServiceImpl.resolveRecvIds 优先用在线集，读失败/为空回退旧路径
- 新增 im.fanout.online-set-enabled 开关（默认 true），支持 A/B 与回滚

两处关键工程决定（都有实测支撑）：

1) 按批 + 流水线，不能逐个用户逐个群地写。
   测试数据里每个用户属于 70 个群，1000 人上线若逐个 SADD 就是 70,000 次独立
   Redis 往返，实测耗时近 1 分钟、事件队列积压 276 条 —— 等于把 O(消息数) 的
   问题换成了 O(用户数×群数) 的登录风暴。改为「整批一次 DB 查询 + 一次 Redis 流水线」
   后，队列 9 秒排空。

2) 用 StringRedisTemplate 而非项目自定义的 RedisTemplate。
   后者 value 序列化开了 enableDefaultTyping，一个 Long 会写成
   ["java.lang.Long",123]，万人群在线集光类型元数据就要多占数倍带宽。

正确性：
- 多终端用户只断一个终端时不能移除，下线按 presence key 判定「最后一个终端」
- 在线集是预筛不是真值来源：多出条目下游查终端 key 会落空，无害；
  少条目对该读扩散群可由客户端拉时间线补齐
- 区分 null(读失败，回退旧路径) 与 空集(确实无人在线，直接返回)

实测（万人群 N=10000、1000 在线、每配置 2 轮、同构建同机）：
  扇出/条 中位   80.0ms -> 40.2ms  (-50%)
    presence      27.2ms -> 0ms     (消除)
    成员列表      16.9ms -> 6.3ms   (-63%)
  端到端 recvMs  20.1/17.5s -> 16.8/15.4s (-14%)
  WS 核对        999000/999000，两配置均 0.00% 偏差

注意 msg/s 这一列反而变差（184 -> 164），因为它是总请求/(sendMs/1000)，
只反映发送阶段。§3.15.3 已论证该列作废，本次再次印证。

遗留：事件消费者仍有 ~9s 排空延迟，来自既有的 sendOnlineStatus（每事件一次）。
若登录风暴更大需一并批量化。
